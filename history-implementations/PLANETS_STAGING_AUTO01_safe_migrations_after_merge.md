# PLANETS STAGING-AUTO01 — Apply safe migrations on merge, without repeated approvals

**Codex implementation handoff.** Goal: once the one-time environment/recovery setup is complete, merging a validated, backward-compatible migration to `main` should normally apply it to **PLANETS staging automatically**, without a second founder approval. Dangerous or unverified changes must stop. This task does **not** authorize a hosted database write, app build/upload, or Play publication.

## Required behavior

1. **Standing authorization for safe staging-only migrations.** After an eligible PR is merged to `main`, the existing protected pipeline checks the exact merged source and automatically applies its required **routine, backward-compatible** SQL migrations to `planets-staging`. No additional approve/waiver prompt for each such migration. Keep the single-writer lock, immutable history, drift detection, fresh main verification, RLS/Storage/grant checks, appropriate populated upgrade rehearsal, and sanitized evidence. A zero-pending run is a verified no-op.
2. **Default-deny risk policy, enforced in CI and at deploy.** Define and document a small, practical classification for safe versus review-required migration effects. Routine means additive/compatible **with no likely data loss, unapproved access expansion, hidden rewrite, or substantial operational risk**, supported by tests. Review-required includes destructive SQL, data rewrites/backfills without proven preservation, incompatible contracts, permission/RLS/Storage weakening, risky privileged-function/trigger changes, stale/missing evidence, unknown history, or anything not reliably classifiable. Do **not** claim SQL is safe merely because a regex found no `DROP`. Check the actual before/after semantics and security tests. If uncertainty remains, fail closed with a clear reason and the exact needed review; never auto-mark an unknown migration safe. A mixed safe/risky pending set must not partially deploy automatically across dependencies.
3. **Put any consequential human review at the PR stage, not again after merging.** `AGENTS.md` already allows automatic PR merging after CI. A migration requiring explicit founder review must therefore block that auto-merge path or carry a verifiable prior owner review bound to its exact content. Merging a PR does not erase evidence of a failed migration safety check. Once a properly reviewed PR merges, do not demand a redundant *deployment* approval for the same exact changes; any drift/new content requires renewed review.
4. **One-time staging/recovery readiness.** Establish an operational policy that can be configured once, not a repeated waiver request. Prefer a verifiable protected backup/recovery route before consequential writes, without assuming a paid Supabase tier or buying services. Any DB dump with Auth/private data must stay encrypted and access-controlled, never in this public repository or readable Actions artifacts; distinguish schema/data recovery from Storage-object recovery and verify a restore path. Do not manufacture a backup, reuse the original task-specific waiver as a blanket waiver, or disable TLS. If an adequate mechanism is unavailable, implement the safe workflow and report the **one-time** recovery decision/configuration that blocks activation; do not secretly deploy.
5. **Separate automatic staging from application delivery.** Maintain `STAGING_AUTO_PUBLISH=false` and keep the current AAB / `planets-play-closed` publication authorization. An ordinary `main` push must **not** automatically upload/publish an AAB or update production/Mock, even if staging succeeds. Do not change app-store tracks, signing, map provider configuration, Edge bundles or provider billing. Preserve manual `inspect`, `deploy`, `build`, `publish` routes with their existing safety contracts.
6. **Remove repeated staging review prompts only when the safety gate is effective.** Staging's current GitHub environment reviewer requirement defeats unattended deployments. Adjust the workflow/required environment policy, and document the needed owner-side change to make staging automatic **only after** CI risk classification, recovery policy, deployment identity and credentials are verified. Preserve main-only restrictions, single-writer behavior and separate publication review. Never bypass protections using an unprotected environment or leaked secrets.
7. **Handle the existing two-file catch-up without weakening history rules.** Preserve the original 26-file evidence, applied-history SHA checks and historical-gap detection. Classify and test the exact avatar and notification SQL at their present SHA-256 values (see `remaining-migrations.json`). Because the avatar file is historical, prepare one **bounded, exact-SHA/predecessor-verified reconciliation** that does not falsely treat it as an ordinary monotonic migration. Document any genuinely necessary *one-time* approval/recovery gate; do not silently extend the old waiver, move the bootstrap boundary, change timestamps, rewrite applied history, or use an unsafe global `--include-all` bypass. After parity, normal future migrations should not reopen this bootstrap step.

## Implementation guidance and tests

Favor a focused extension of the present `scripts/release` architecture, not a rewrite/new deployment stack. The approval/risk decision must be deterministic, testable, specific to a canonical migration version/hash and observed predecessor, and resilient to an advancing `main` or concurrent writer. Do not add a new ongoing founder approval ritual disguised as a “safe” manifest. Prefer reuse of existing exact-source CI and synthetic populated rehearsal; avoid duplicating entire CI on routine doc-only commits.

Add/extend targeted tests in `scripts/lib/release01.test.mjs` (or a focused sibling) covering:

- ordinary eligible migration: merged validated SHA → permitted staging set without post-merge approval;
- risky/unknown migration, RLS grant expansion or function replacement with uncertain semantics → blocks prior to automatic deployment; explicit pre-merge review pathway;
- stale SHA, altered canonical SQL, remote drift, unexpected historical gap, mixed pending set, missing recovery readiness, failed rehearsal/CI, wrong staging identity, missing secrets, concurrent run → fail closed;
- two-file historical reconciliation: only exact reviewed SHA + predecessor, no blind chronology bypass; no-op retry after application;
- staging success never activates Android/Play publication; `STAGING_AUTO_PUBLISH=false` and mock/production separation remain intact;
- no secrets/personal data in logs, test artifacts or recorded approval evidence.

Run `node --test scripts/lib/release01.test.mjs`, `npm run test:tooling`, formatting/actionlint, affected CI, and the disposable populated migration rehearsal. Run complete four-area Validation for this cross-cutting release change. Report actual outcomes rather than assuming tests passed; do not use a populated hosted database as test data.
