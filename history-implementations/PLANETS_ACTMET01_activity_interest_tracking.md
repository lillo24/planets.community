# PLANETS ACTMET01 — Activity Interest Tracking (Card Opens + Shares)

## Objective

Add a small, explicit **activity-interest analytics** slice so PLANETS can later assess which real activities attract attention. Measure (1) taps that open an activity's detail from a card and (2) deliberate public-link sharing actions. Keep the two actions separate and accurately named. The immediate output is internal analytics and testable instrumentation—not a user-facing popularity rank or “affollato” indicator.

**Parallel delivery:** implement this on a separate branch/PR from **ACTAPI01** (official-API importer). Do not require ACTAPI01 to finish before useful work can merge. Reconcile with its future real imported-activity models at integration time rather than guessing their schema now. This is one focused prompt; do not expand into the full analytics roadmap.

## Decisions and measurement semantics

Instrument only **real, public activities**:

1. `activity_card_opened`: one explicit tap on a valid card that starts navigation to that activity's detail. This is a *card-to-detail navigation intent*, **not** an impression, unique visitor, confirmed completed page view, or attendance. Do not fire from widget builds, list loading, filter changes, returning to a route, background restoration, or direct deep links. Use a stable source/surface label to distinguish native Tavoli from future imported activities.
2. `activity_share_action`: one explicit public-share handoff, with `action=link_copied` only after a successful clipboard copy, or `action=share_sheet_invoked` after the app successfully invokes native sharing. The native share sheet may be dismissed; **do not claim that a person actually sent the link**. No event on merely opening a share dialog, canceling it, an invalid link, failed copy, or failed share invocation.

Do not track the 12 sandbox examples, drafts, unavailable/unauthorized records, or native Progetti and Scambio-Dona. Do not add analytics to private chats, invitations, participant links, direct messages or any capability-bearing URL. Do not infer event attendance, actual venue crowding, demand versus capacity, or “popular enough to be full” from these actions. No public counts, recommendations, ranking changes, or “Affollato” badges in this plan.

Use a tiny, typed, versioned event vocabulary with a strict allowlist of safe attributes: event name, **canonical public item kind** (`tavolo` / eventually `imported_activity`), **stable non-secret public item ID**, explicit origin surface (`tavoli_list`, future `activities_list`), action/method when applicable, and optional coarse app version/environment. Never send item titles/descriptions, organizers' contact info, raw URLs, query/search text, exact location, login identity, email, profiles, invitation tokens, chat text, content metadata, IP addresses from the client, or user-generated parameters. The shared track API must reject invalid kinds/IDs rather than emitting arbitrary client properties.

A card can be tapped more than once over time: raw taps are useful, but are **not unique people**. Prevent double-emission from one gesture, duplicate callbacks, rebuilds, pending async work and accidental rapid double-taps where practical. Do not create long-lived user identifiers or device fingerprints merely to deduplicate.

## Analytics architecture and privacy boundary

Build a lightweight app-owned `ActivityInterestTracker` (or equivalent) with a no-op sink, a fake/in-memory sink for tests, and a **manual-events-only PostHog EU adapter** consistent with the accepted stack. Reuse existing config/bootstrapping, Riverpod/test seams and the repo's pinned dependency conventions. Verify the SDK's real API/version before coding against it. No generic analytics bus, notification engine, backend event table or custom aggregation service is required.

**Critical activation rule:** transport is **OFF by default**, including in release builds, until both explicit configuration and an approved analytics permission/legal basis are supplied. The Activities Split Mode setting is **not** consent, and accepting Terms/Rules is **not** consent. Implement a testable policy gate/interface whose default is denied. Do **not** silently add an opt-out tracking default, fabricate legal approval, or turn a sandbox UI switch into analytics consent. If a user-facing consent control or policy change is required for genuine activation, report that as an owner decision and leave live transmission disabled; don't write provisional consent wording as though approved.

When the sink is disabled, there must be **no PostHog initialization, HTTP traffic, persistent analytics ID, local event cache, or SDK auto-collection**. When explicitly configured/authorized, use the verified EU ingest endpoint and manual capture only: disable autocapture, session replay, screen recording, automatic screen views, automatic identity/profile enrichment and automatic person identification. Do not `identify` accounts or capture account IDs. If an SDK cannot meet these constraints or necessarily persists a stable cross-session identifier, fail closed and report the limitation rather than silently weakening the privacy contract. Keep a documented maximum event volume or simple bounded queue/flush behavior; no unbounded offline persistence. No production credentials required for local tests; never commit keys/secrets.

Tracking is **best-effort and non-blocking**: an analytics error, disabled gate, timeout, slow network or disposal must never prevent card navigation, copying, native sharing, or normal app behavior. Do not surface telemetry failures as user errors or dump event payloads into logs/Sentry. Provide a deterministic fake sink so local tests can inspect exactly what would have been captured, without external network calls.

No migration, admin dashboard, public popularity endpoint or deployment is part of this slice. PostHog is for **internal product analytics**, not the canonical representation of event attendance or registration state. If a future feature needs user-visible occupancy, it needs independent organizer/booking/capacity evidence and a separately reviewed specification.
